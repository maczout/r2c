## Held-out rule

**Kept**, with one thing that came close to the line. The first set was scored once, at
the end, with the kernel as committed; only the printed totals and kinds were read;
nothing under the archive's results folder was opened, r2c was not run on a held-out
input by any other route, and every cause above was found on development cases. The
second set was not touched. Response against itself (`tools/heldout.py repeat`) is the
owner's instruction: it runs Response on the held-out inputs with their concrete
strengths raised, compares Response with Response, prints totals only, and leaves its
captures and comparisons in the archive, unopened; no r2c result is in it. Close to the
line: while the scorer was running, a switch that is off (a faster pass of the layer
splitting, for the next increment) was written into `src/r2c/solver.py` and taken out
again about half a minute later, so a case the scorer started in that half minute read
the file with it. With the switch off the file does what the committed one does: a copy
of the tree with it gives the same records, byte for byte, as the committed kernel on
the development cases run from it (see Evidence). The switch is not in the repository.

**Shear, priority 1 fell: 27 to 26 of 28** (the floor; in the summary for the owner).
The kind the scorer prints as newly outside: a rectangular beam under moment and shear,
M/V under 2 m. Looked for on the development set, not on the held-out one: no
development case of that kind left priority 1, but two cases show what Response's solve
can do to a rising branch. On Newbeam under a moment, then shear alone (newbeam-m50-v:
rising branch 1.7 to 10.2 %) the stage at the fall of load when the web cracks does not
settle, and r2c keeps it at 152.7 kN and a shear strain of 2.35 mm/m where Response
keeps 176.3 and 1.93; the stages before and after agree to a thousandth. On Newbeam in
US units at M/V = 1 m the fall comes one stage later in r2c. Inferred, not measured:
that the held-out case is of this sort. Not recovered in this increment: no rule was
found for which state a stage that does not settle is left in, and the set was not
scored again. After the score, with the kernel left as scored: under shear alone r2c still damps the
profile update in the second half of the passes (`Shear.relax`, r2c's own, from before
Response's solve was on). Without it (`python tools/trial.py ... --set Shear.relax=1`,
the eight development cases under shear alone) newbeam-m50-v is back inside priority 1
and 3 (rising branch 11.0 to 0.9 %), one more case comes inside priority 2 and one
priority 4, and none goes outside on a priority. It is the first thing for the next
increment (`docs/status.md`). It does not reach the kind that fell on the held-out set,
which is not stepped in the shear strain.
