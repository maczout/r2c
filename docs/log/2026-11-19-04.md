## How the binary was read

The repository had not said. Ghidra 12.1.4, headless, JDK 21, at `$GHIDRA_HOME`; r2k.exe
1.9.7 (SHA-256 bbf4bc59…4e74) imported and auto-analysed by the owner in the project
`~/ghidra-projects/r2k`. Both outside the repository; so is every line of decompiler output
(kept in a folder outside it while working, not committed).

`tools/decompile.py` runs `analyzeHeadless … -process r2k.exe -noanalysis -readOnly` with a
GhidraScript written in Java to a temporary folder. Java because it runs in headless Ghidra
as installed; Python scripts need PyGhidra set up (Jython is no longer the default). The
project is opened read-only, so reading cannot change it. A run takes about 5 s.

Check that the addresses line up with `docs/status.md`: `004ad9c0` decompiles to a routine
that switches on a tension stiffening model and returns a stress scaled by the concrete's
factor: the concrete stress routine.

The reading went by following calls from `0041e840` (which names itself: "Calculated Shear
stress distribution"), and by searching for the instructions that use a structure offset to
find what writes a field. `00417290` turned out not to be the shear driver. Addresses of
what was read are in the table of `docs/status.md`, section 7.

  first cracking it gave one node a stiffness of −6·10⁷ MPa (Newbeam M/V = 1 m, stage 10:

  at M/V = 1 m, a well-matched case, 22 % past Response's failure (the brief's first stop
